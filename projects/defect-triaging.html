Building an AI Domain Expert When You Don't Own the Domain Yet

Structured Knowledge Base first. Personas that think like senior engineers second. Triage only when both are real.

2–4 hrs → <35s
Manual RCA time vs. pipeline RCA time
Live
In production today

I joined a telecom charging platform I didn't understand, and the fastest way to learn it turned out to be building an AI that had to explain it back to me.

That AI is now running in production: a structured Knowledge Base, a Domain Expert persona for Q&A, and an evidence-based Triage Analyst for live defects — cutting root cause analysis from 2–4 hours to under 35 seconds.

The interesting part isn't that it worked. It's what had to be true first — and how you build a knowledge base for a domain you don't own yet. The pattern transfers better than the telecom specifics.

The KB is the product. Personas, prompts, and tool integrations are just the interface — every later capability stands on whether the catalog can answer where you are in the domain.

The lesson up front: the KB is the product

Personas, prompts, and tool integrations are the interface. The Knowledge Base is the foundation.

Skip it, and a "domain expert agent" is just fluent guesswork. Skip it in triage, and you get a confident monologue instead of an investigation. Every later capability — Expert Q&A, flow mapping, confidence caps, ingestion — stands on whether the catalog can answer four questions:

  • What family of behavior is this?
  • Which flow am I in?
  • Who owns the contracts (errors, interfaces)?
  • What do we know vs. guess?

Rebuild this tomorrow, and I'd still spend the first stretch on KB design, not chat UX.

When the KB source is completely new

That's the hard case: you don't know yet which docs matter, what's authoritative, or how experts mentally carve up the domain.

What "new source" looked like

The material: a large architecture and design corpus — flow references, interface docs, diagrams — plus code and ticket history. I didn't have a mental map. Dumping all of it into embeddings would have just built a search engine over confusion.

How we ran discovery

  1. Inventory before interpretation. We didn't summarize random pages first. We ran discovery over the source tree, mapping flow references into a full inventory. Not "understand everything" — just: what flow references exist, which look like core lifecycle vs. specialized families, where do diagrams and text disagree, what belongs in a first useful catalog. Discovery produces candidates, not a finished KB.
  2. Draw a hard scope line early. From discovery we indexed core session and event coverage and left specialized, lower-frequency flow families out — even though they showed up in the tree. An unbounded corpus never becomes trustworthy. Completeness of discovery isn't completeness of indexing. Write out-of-scope in public, so the agent doesn't invent coverage.
  3. Choose one pilot and make it deep. We picked one pilot flow and went deep: message sequence, systems sequence, error catalog, interfaces, runtime-evidence pointers. Variants reuse the pilot instead of cloning catalogs. On a new domain, depth on one golden path beats shallow coverage of twenty — the pilot becomes the template for everything else.
  4. Group by ingress, not by document title. Documents aren't the unit of reasoning — ingress signals are: what entered the system, on which protocol, for which purpose. That became the navigation spine. Structure the KB the way an engineer debugs: what entered the system, not which document mentioned the error.
  5. Validate with scenarios, not vibes. Every expansion phase ended with scenario checks: can the agent distinguish protocols, pick the right flow, name the right owner? We kept a validation score and an accepted-gaps list so thin areas stayed visible. A KB without tests ages into fiction — scenario Q→A is the unit test of domain knowledge.
  6. Separate catalog truth from runtime fetch. The KB holds structured facts and pointers. Live code and design docs get fetched when the catalog runs out, so the KB never becomes a stale code dump. Index what's stable; point to what moves.

Playbook if your source is new

  • Dump the corpus into an inventory, not into answers
  • Pick the ~20% of flows that cover ~80% of day-to-day questions
  • Build one pilot end-to-end
  • Write 10 scenario questions; iterate until the KB answers them with paths
  • Only then add Expert Q&A
  • Only then add investigation that uses the KB + live evidence
  • Instrument feedback from day one of any pilot

Abstracting AI personas: teaching an agent to think like a senior engineer

Once the KB could answer "where am I in the domain?", the next problem was different: how should an agent think when something is broken?

Most triage bots collapse into one move: read the ticket, pick a familiar component, write a root cause. That's not how strong engineers work — so we abstracted senior-engineer troubleshooting into personas: role identity, reasoning rules, tool gates, an ordered workflow. Not a single clever prompt.

If your "agent" is only a system prompt, you haven't abstracted the role yet. Abstract the decision discipline.

Same foundation. Different cognitive job. Keeping them separate stops the Expert from "triaging" every question and the Triager from lecturing architecture when the ticket needs log analysis.

How I used the Expert while learning

Instead of interrupting seniors constantly, I asked the Expert: how core flows worked, why interfaces existed, what triggered downstream processes, how session lifecycle and billing events connected end to end. It doesn't invent a second truth — it reads the KB, then escalates to code or docs when needed.

Triage Analyst: the senior-engineer operating system

Your job is not to confirm a hypothesis quickly. Your job is to build an accurate mental model of the defect from primary sources.

That fights the default model habit: pattern-match early and defend it.

Seven principles we encoded

  1. Evidence before conclusion — No RCA without a primary source. Gaps stay pending, not filled with confidence.
  2. Start wide, narrow with facts — Don't pre-select a favorite component; every narrowing step cites what forced it.
  3. Hypothesis ledger, not fixed RCA — Theories stay open / confirmed / rejected, even against a senior's earlier comment.
  4. Verify, don't trust — Prior RCAs and "already fixed" comments are claims, not facts. Latest retest and current code win.
  5. Separate layers — Logic ≠ persistence ≠ query/filter ≠ API mapping ≠ downstream display.
  6. Confidence is earned — Per finding, from evidence quality. Low confidence is allowed; false certainty isn't.
  7. Multi-symptom by default — Bundled symptoms are independent until proven shared.

The investigation loop

  1. Live ticket (full comments + attachments)
  2. Symptom & impact
  3. Verify prior investigation (accept / reject / partial)
  4. KB flow map (where this sits in the domain)
  5. Candidate routing only after evidence
  6. Code / design / bugfix branch when needed
  7. Update hypothesis ledger
  8. RCA only when supported — or "blocked pending evidence"
  9. Confidence + checkpoints + next actions
  10. Audit saved
  11. Human feedback
  12. Improve the workflow

Two choices matter more than prompt length:

  • Post-evidence repo routing — No locking onto a component before reading the ticket.
  • KB as the map, not the verdict — Place the defect in a flow family before diving into the wrong codebase.

What "like a senior engineer" means in the output

A junior dump says: Root cause is X. Fix file Y.

A senior-style report makes reasoning inspectable: answer with confidence, hypothesis ledger, tagged sources (ticket / code / KB / attachment / inference), validation still required, and checkpoints that passed or remain open.

That turns the agent from an oracle into a pair investigator — something a human can disagree with productively.

Humans still own the truth

The loop in production:

  1. Run the defect through the Triage Analyst first
  2. Review the analysis
  3. Investigate with real experience
  4. After conclusion, leave feedback: what helped, what was wrong, what was missed

Feedback is stored raw. Action items feed prompt, KB, and workflow. Accuracy keeps rising because experienced engineers keep using it — not because anyone trusted the first good-looking report.

Build the agent to be reviewed, then instrument the review.

What worked — and what was harder

Worked

  • Treating the KB as the product and personas as consumers of it
  • Discovery → scope → pilot → validate before breadth
  • Pilot/variant reuse so contracts don't drift
  • Explicit confidence caps and accepted gaps
  • Hypothesis ledger + anti-patterns in the triage persona
  • Audit + feedback so wrong answers become backlog, not folklore

Harder than expected

  • Diagram titles vs. protocol reality (document the conflict; don't silently pick)
  • Thin source references on some variants — better to mark medium confidence than overclaim
  • Resisting the urge to index everything discovery found
  • Stopping the agent from "winning" with an early RCA

Ongoing

  • Expanding scenario coverage as new defect patterns surface in production
  • Aligning with other triage-agent efforts toward a shared pipeline

Closing

We didn't try to make the agent "smart." We tried to make the domain navigable and the investigator disciplined.

The Knowledge Base tells the agent where it is. The persona tells it how to think once it's there. Neither alone is enough. Together — with humans reviewing and feeding back — they approximate a senior path well enough to accelerate learning and triage in production, and stay structured enough to be corrected in public.

Start with discovery, scope, and a structured KB that can be wrong out loud. Then teach the agent the habits of a senior engineer — not the performance of one.
