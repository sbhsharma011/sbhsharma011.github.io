JobPilot — AI-Assisted Job Application Autofill

A Chrome extension that fills out job application forms across any ATS platform, matches your profile against a job description before you apply, and stops you from accidentally applying to the same role twice.

View on GitHub ↗
Manifest V3 Vanilla JavaScript Anthropic Claude API

The problem

Job searching means re-entering the same information — name, contact details, work history, EEO answers, "why do you want to work here" — into dozens of different application forms, each built on a different ATS (Greenhouse, Lever, Workday, iCIMS, or a fully custom portal). Every platform structures its form differently: some are plain HTML, some are React-controlled inputs, some render dropdowns as portaled JS widgets with no relationship to a native <select>. Autofill tools that work on one break on the next.

I built JobPilot to solve this for my own job search, then cleaned it up as a public project once it was solid enough to be useful to others.

What it does

  • Two-layer form filling. Simple text fields (name, email, phone, location) are filled instantly through local label-to-profile-key pattern matching — no network call, no latency, no cost. Everything else — selects, radio groups, free-text screening questions, custom dropdowns — goes to a single batched Claude API call that receives the full option list per field and picks the correct answer in context.
  • Profile match scoring. Before applying, JobPilot scores your profile against the job description and shows what you match, what's missing but reasonable to claim, and what would misrepresent you. Gaps that keep recurring across many job descriptions get tallied over time (grouped by underlying concept, not exact wording, so "change management" and "managing organizational change" count as the same signal) — turning scattered rejections into a concrete list of skills worth actually adding to your resume.
  • AI cover letters. Generates a tailored cover letter grounded in your profile and full resume detail, exportable as a PDF.
  • Resume-driven setup. A first-run wizard takes a PDF/DOCX/TXT resume and uses Claude to extract your profile automatically — name, contact info, work history, a written summary, and skills — instead of a blank form. The same rebuild is available later from Settings whenever you update your resume.
  • Duplicate-application tracking. JobPilot fingerprints each job posting (via embedded JSON-LD JobPosting metadata when present, otherwise page title/heading heuristics, falling back to a hash of the URL) and warns you before you re-apply to a posting — or a similar role at the same company — you've already marked as applied.

Engineering highlights

Filling framework-controlled inputs

Setting .value directly on a React- or Angular-controlled input does nothing useful — the framework's internal state never sees the change, and the form re-renders the old value. JobPilot uses the native HTMLInputElement property setter (bypassing the framework's overridden setter) and dispatches input/change/blur events afterward, which is what actually gets picked up by React, Vue, and Angular's own change-detection.

Reverse-engineering custom comboboxes

Many ATS platforms (react-select, MUI Autocomplete, and various Greenhouse/Ashby-style widgets) render what looks like a plain text input but is actually a JS-driven dropdown with a portaled options list — sometimes attached to <body>, not nested near the input. Typing into these and reading .value back doesn't register a selection with the framework; only clicking the rendered option element does. JobPilot detects these via ARIA attributes (role="combobox", aria-autocomplete, aria-haspopup="listbox"), types the target value character-by-character to trigger the framework's own filtering, polls for the rendered option list with tolerance for debounced/async filtering, and simulates a full pointer event sequence (pointerdown → mousedown → pointerup → mouseup → click) on the matched option — since several of these libraries bind their selection handlers to pointer events rather than click alone.

Dependency-free file handling under a strict CSP

Manifest V3 extension pages run under script-src 'self', which rules out loading a PDF or DOCX library from a CDN. Both had to be built from scratch: a PDF generator that hand-writes valid PDF 1.4 object/xref structure and does its own word-wrap using canvas font metrics (no library, no font embedding — just the standard Helvetica base-14 font every PDF viewer ships), and a DOCX reader that walks a .docx's ZIP central directory by hand, decompresses word/document.xml using the browser's built-in DecompressionStream, and strips it down to plain text.

Knowing where it stops working

Some modern ATS platforms (ADP's Angular-based application flow among them) render their entire form inside Shadow DOM via a component library, which a content script's document.querySelectorAll fundamentally cannot see into — shadow trees are separate node trees from the main document. Rather than silently failing, this is a documented, understood limitation with a clear reason, not an unexplained gap.

Privacy by design

Profile data and the Anthropic API key live only in chrome.storage.local — never synced, never sent anywhere except the user's own calls to the Anthropic API. LLM requests include only field labels/options and a compact version of the profile; the API key itself never appears in a prompt.

Tech stack

  • Vanilla JavaScript
  • Manifest V3 — service worker background script, on-demand content script injection, side panel UI
  • Chrome Extension APIs — scripting, storage, sidePanel, activeTab
  • Anthropic Claude API

No build step, no frameworks, no external runtime dependencies — a deliberate constraint that shaped several of the harder engineering problems above.
